# PR32 生产前修复与容量证据

## 两项阻塞修复

1. profile 直接调用 `WriteSinkEvent`，控制台不含 profile 并通过 skip 标志避免重复入库。真实 middleware → OpsSystemLogSink 反例已验证：sampling initial=1/thereafter=100 时，10 条 200 请求完整进入 sink，未重复；禁用和拒绝保护继续生效。5007 条请求填满 5000 条队列时，明确报告 7 条丢弃。
2. 未发布的迁移237改名为 `237_request_profile_lookup_notx.sql`，使用 `CREATE INDEX CONCURRENTLY`。在独立 PostgreSQL 中持有旧写事务，让真实迁移保持进行中，再从第三连接插入：约0.39ms完成，索引随后有效。此证明写锁兼容，不承诺大表建索引没有CPU/I/O成本。未在生产运行迁移。

## 合成负载实测

Apple M5，本机独立 PostgreSQL cluster，仅该测试使用。真实 middleware、Snapshot/partition、真实有界 sink、真实 PostgreSQL COPY 入库；控制台级别 warn。普通形状20 spans/12 events，边界形状512 spans/128 events。它是代表性元数据形状的组件负载，不是生产 QPS 或模型端到端时延认证。

¹ 包含夹具与异步落库分配，不是单条常驻内存。JSON TOAST 压缩使合成重复内容较省空间；不能据此给真实生产磁盘/WAL下界作保证。峰值队列来自未限速突发，不能当作稳态生产容量。

另外保留了一个不利观测：未等队列完成就立即 Stop 时，首次测试出现在途200条写失败及1400条剩余丢弃，计数均可见。共享 sink 的停止/数据库故障期间依然是尽力而为；不得把关闭测试中的丢失隐藏成稳态零丢失。

## 上线限制

- 默认改为 **false**。上述微基准不足以授权生产全量开启。
- 共享队列仍是5000条且没有字节预算；512/128只限制数量，不是字节上限。不能将JSON平均大小当作Go内存上限。
- 共享30天留存、24小时JSON聚合仍有累计风险。粗估普通样本1QPS的30天JSON原文已约7.5GB，真实模型/事件分布与索引/WAL另计。无独立容量/留存方案不得无期限开启。
- 实际发布前必须确认目标真实QPS、记录大小分布、磁盘/WAL/数据库余量、采集队列水位、查询耗时与应用SLA/TTFT变化。可用数据与安全启用必须一起验收，不能只发布空页面，也不能用瞬时测试替代容量验证。
- 若需要持续全量采集，应先补足 profile 字节预算、专属留存/清理以及查询成本控制，或给出目标环境验证过的等价限制。任何丢弃须继续明确展示。
